# Task 0040: Ingestion API contract for sending systems

Written: 2026-11-21, by the design chat. Branch: `docs/ingestion-contract`, taken from `release/vero-r7` **after task 0039 is merged**. Docs and tests only; no product behaviour change (if the contract test finds a real mismatch, stop and report it).
Why: LexaVault (and every other sending system) will build against Vero's ingestion API as a ready-made profile checked by contract tests (LexaVault thread, 2026-11-21). The OpenAPI file must be complete, stable and enforced.

## What to do

1. **`docs/api/sdv-ingestion-v1.openapi.json` is the contract.** Make it complete for a sending system:
   - every ingestion operation, header (`X-SDV-*`, `Idempotency-Key` or whatever Vero uses), body field (including `recordSensitivityLevel` and the per-document level header), and every response;
   - **readiness**: document `/actuator/health/readiness` as the "can I send now?" check (UP = send; not ready or 503 = wait and retry, never a refusal);
   - **sign-in**: the `bearerAuth` scheme in full: OAuth2 client-credentials tokens from the customer's login server; required claims (audience, the configured tenant-ID and source-ID claims, subject); what each missing or wrong claim returns (AUT codes);
   - **every answer a sender can get**, with status and code: success (201 received; 200 already received for a retry; 200 `DUPLICATE_ALREADY_STORED`), refusals (all `SDV-INT-*`, `SDV-SEN-*` and sign-in codes that ingestion can return), retryable failures (429, 503 with SYS-014 / AUT-004 / STO-001, 500), each saying **retry or don't retry**;
   - the common error body `{code, message, reference, timestamp}`.
2. **Versioning policy** in `docs/api/README.md`: the path version (`/v1`) stays backward compatible; additions are allowed (new optional fields, new codes); anything that breaks a sender (removing or renaming a field, changing a status or a code's meaning) needs `/v2` and a notice period. The OpenAPI `info.version` follows semantic versioning; record each change in a changelog section.
3. **Contract test in Vero:** a test that fails if the running API and the OpenAPI file disagree (paths, headers, status codes, error codes listed per operation). It runs in the normal build.
4. **A sender's guide** (short) in `docs/api/README.md`: how to set up a sending system (client in the login server with the tenant-ID and source-ID claims, audience), a worked example of one submission with two documents, and how to read each answer.
5. **Live check with a machine token:** with Vero in `enterprise-jwt` mode (`Start-SDV-OIDC.ps1`) and a client-credentials client in the local `lexa-keycloak` (claim mappers for tenant ID and source ID), send one submission and one document. Report exactly how the client was set up. Do not change Keycloak's other clients or realms; create a clearly named test client, and say how to remove it.

The "tenant" claim will be renamed "entity" (`ENT-…`) at the same time. This is a relaxation for senders, not a break.

1. **Busy answer.** When Vero is too busy to take a request (for example the intake or database pool is full), it answers **503 with a documented busy code** (next free `SDV-SYS-…` number, plain message) **and a `Retry-After` header** (seconds). No 429. Every other 503 means unavailable (as now: SYS-014, AUT-004 and so on) and carries no busy code.
