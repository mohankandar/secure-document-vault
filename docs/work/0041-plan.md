## 2. Conflicts with the rule (identity only), each with a proposal

**C1. Setup needs the licence.** The rule says licensing waits.

What setup takes from the licence for identity:
- the customer ID (`tenantId`), which must equal the sign-in file's;
- the customer name, for `idn_customer`;
- the **entity slot IDs**, for `idn_entity`; mapping rows and bindings must name them;
- the **product list**: the product must be in it (`SETUP_PRODUCT_NOT_IN_LICENCE`);
- the **signing key**: development or not, which decides whether a local `http` issuer is allowed.

Setup also **stores the licence** in `lic_` (it checks `lic_` tables at their version, `SETUP_TABLES_NOT_READY`). It refuses an older licence than the stored one. It writes `platform-tenant.properties` (`platform.licensing.tenant-id`).

**Proposal (as SH-10 and LV-14/15 say):**
- The schema step creates the identity **and licensing** tables.
- Setup stores the development-signed licence locally.
- Vero does **not** add `platform-licensing-spring`, does **not** import `platform-tenant.properties` as a licensing setting, and checks no allowance.
- The install guide gets the line "Until the app turns licensing on, the licensing tables and the stored licence exist, but nothing checks the allowance. Licensing is not live."

Open part: Vero's runtime may need the customer ID (C2), and production installs need production trusted keys (C7).

**C2. Two runtime places read the licence indirectly.**
- (a) `SlotActivation` (Business Admin activation) needs `LicensedSlots`, which `LicenceSlots` gets from `LicenceService`, so it reads the stored licence.
- (b) A local `http` issuer for a connection made in the IT Admin screen needs `DevelopmentLicence`, which `LicenceSigningKey` gets from `LicenceService` plus the trusted keys.

**Proposal:** allow both **read-only** licence reads, for identity only. They check the licence period and the slot list; they never count or limit anything. If the owner does not want that, then:
- (a) the demo step activates slots through platform-core (C6), with no in-app activation;
- (b) `DevelopmentLicence.NONE`, so an `http` issuer comes only through setup.

**C3. The setup tool carries other modules.** `platform-setup` depends on `platform-crypto` (customer keys in Vault Transit) and `platform-integration` (it checks `integrationProfiles`).

**Proposal:** they are on the **setup wrapper's** classpath only (1.1), never on the app's. Using them inside the setup tool is not an integration by Vero. Vero's sign-in file lists no `integrationProfiles`.

**C4. The test sign-in's production fetch is in `platform-integration`** (`OutboundIssuerFetch`). The IT Admin "test" step needs an `IssuerFetch`.

Proposals, in order:
- (a) allow `platform-integration` on the app's classpath **for `OutboundIssuerFetch` only**: the release notes place it with the identity feature, and it keeps the outbound rules in one place;
- (b) Vero writes its own small `IssuerFetch`: https only, no redirects, no internal addresses;
- (c) the screen offers no test sign-in until the integration release, and only setup changes the connection.

I recommend (a) (Q6).

**C5. `PLATFORM_OPERATIONS_ADMIN` cannot be granted** through the mapping file, and platform-core gives no other way in 0.2.0.

**Proposal:** one setting, `sdv.auth.platform-operations-groups` (a group list). It is the only group setting left, and it is not an entity grant. Alternative: the role is unused until platform-core offers a way (Q4b).

**C6. No activation screen in Vero.**
- Demo and local: the demo step activates the slots.
- Production: the Business Admin needs an "activate entity" action. **Proposal:** a minimal admin API, `POST /api/v1/admin/entities/{slotId}/activate`, which calls `SlotActivation.activate`, creates the `tenants` row and writes an audit record. The screen comes as a UI task (Q11).

**C7. Production trusted keys.** Setup needs `--keys`. A production Vero release must ship `trusted-keys.json` with **production** public keys, exported with `issue-licence --export-trusted-keys`. Vero has none.

**Proposal:** the release folder holds no `trusted-keys.json` until the owner supplies it. The wrapper refuses with a clear message when the file is missing. The development keys file is never in the distribution, and a test checks this.

**C8. Customer keys in Vault at setup time** (LV-15: setup creates them). Setup's Vault login needs the `platform-crypto-setup` policy and a Transit mount on `sdv-vault`.

**Proposal:**
- The owner creates the policy, the mount and a setup token file under `C:\dev\sdv\secrets`. I never open or create anything there, and I do not initialise, reset or reseal the Vault.
- The wrapper passes `PLATFORM_SETUP_VAULT_TOKEN_FILE`.
- Until the owner has done that, local demo runs may use `--no-customer-keys` (allowed, `"customerKeys": "optional"`) (Q12).

**C9. Old local data under `1111…` and `2222…`.**
- The local `sdv` database holds real development data under the old entity UUIDs. Changing to derived UUIDs leaves those rows without an identity entity.

## 3. What changes for senders

- **The entity and source come from the verified client ID, never from claims.**
  - The client principal is read from the claims listed in `sdv.auth.jwt.client-id-claims`, default `azp,client_id,cid` (Keycloak `azp` / `client_id`; Okta `cid`). If they disagree, the call is refused.
  - `PostgresMachineEntityBindings(ds, PRODUCT).find(connectionKey, clientId)` then gives the entity: the binding must be ACTIVE, the entity ACTIVE, and the customer's login connection for the product ACTIVE. `MachineEntityAdmission.requireUnique` admits exactly one.
  - `PostgresMachineClients.activeBinding(clientId)` gives the **source key**. Vero maps it to the `ingestion_sources` row of that entity, which must be ACTIVE.
- **What counts as a machine token:** a token whose client ID has an ACTIVE binding.
  - A token with a binding **and** groups is refused, as today (`SDV-AUT-005`).
  - A token with no binding and no groups is refused: it is not a person and not a sender.
  - People's browser client (`sdv-web`) is never bound.
- **Claims become optional and must match.**
  - `sdv_tenant_id` is **renamed** `sdv_entity_id` (entity UUID).
  - `sdv_source_id` stays (source UUID); `sdv_source_key` may be accepted as well.
  - If present, each claim must equal the binding's value, otherwise the call is refused.
  - Proposal: **no** fallback that reads the old `sdv_tenant_id`, because no old references stay (Q13).
- **New refusals, recorded as intake failures** (`IntakeRefusals`; unknown entity → `unidentified_intake_attempts`):

  | Code | When |
  |---|---|
  | `SDV-AUT-011` | no ACTIVE binding for this client ID (or the entity or connection is not ACTIVE) |
  | `SDV-AUT-012` | the entity claim or source claim does not match the binding |
  | `SDV-AUT-013` | the binding's source has no ACTIVE source in Vero for that entity |

  Numbers are final once Q5 settles `SDV-AUT-010`.
- **`SDV_REQUIRE_CLIENT_BINDING` is not needed.** The binding is always required, and there is nothing to switch. Recognising senders by claims goes away entirely.
- **Contract 1.1.0:**
  - `docs/api/sdv-ingestion-v1.openapi.json`: `x-sdv-required-claims` loses `sdv_tenant_id`; the optional claims become `sdv_entity_id` and `sdv_source_id`, which must match.
  - The sender's guide (`docs/api/README.md:36-70`): standard client-credentials token, no custom claims needed; the line 49 "planned change" note is removed; the token example uses the "Redaction Service" name.
  - Changelog 1.1.0, and the tag `sdv-ingestion-v1.1.0` at the merge.
- **Live check (Part B 7):** in client `sdv-0040-contract-test-ingestion`, remove the two `sdv_*` mappers and keep the audience mapper. Bind its client ID to `ENT-VERO-DEMO-0001` and `redaction-service` in the demo binding file.
