## What was done

1. **Append-only audit trail, held by the database** (changeset `037-sealed-audit`):
   - A trigger function `sdv_refuse_append_only_change` refuses UPDATE, DELETE and TRUNCATE on `audit_events` and on the new `audit_reports`, for every user, including the table owner. The message starts with `SDV-AUD-017`.
   - UPDATE, DELETE and TRUNCATE are revoked from `public` and from every grantee other than the owner. The runtime (read/write) user keeps SELECT and INSERT only.
   - The clean-install runbook says the same.
2. **The report register**: a new `audit_reports` table. It holds who generated each report, when, the period, the filters (jsonb), the event count, the SHA-256 fingerprint (checked: 64 lowercase hex characters), the CSV bytes and the checks. It has no update or delete path in code, and the database refuses both.
3. **Generate**: `POST /api/v1/audit-reports`.
   - The period is whole UTC days, both included. The Audit list's filters apply: result, action, record number and level.
   - The limit is 10,000 events (SDV-AUD-013). Events come oldest first.
   - The report is registered and `AUDIT_REPORT_GENERATED` is audited in one transaction.
4. **CSV for machines**:
   - The file starts with a stamp: report reference, generated by, generated at (UTC), first and last day (UTC), filters and the event count.
   - Then the Audit list's CSV header and rows: document IDs and record numbers only. It never holds content, file names, titles or reasons.
   - The fingerprint is the SHA-256 of these exact bytes.
5. **PDF for people**: made from the same CSV with PDFBox (already a dependency), A4 landscape. It shows the stamp and the fingerprint, with a footer on every page.
6. **Downloads**:
   - `GET /{id}/csv` and `/{id}/pdf` each audit `AUDIT_REPORT_DOWNLOADED`.
   - They send `X-SDV-Export-Reference`, `-Fingerprint` and `-Rows`.
   - The file name is `vero-audit-report-<first day>[-to-<last day>]-<id8>.csv|pdf`.
7. **Verify**: `POST /verify` takes a fingerprint and says whether it matches a registered report, and which one. It audits `AUDIT_REPORT_VERIFIED`. On the screen, the CSV's fingerprint is worked out in the browser; the file is not sent.
8. **Who may**: new capability `GENERATE_AUDIT_REPORT`, for Business Admin and IT Admin only. Everyone else gets SDV-AUD-010, audited as `AUTHORIZATION_DENIED`. There is no auditor role.
9. **Error codes** SDV-AUD-010 to -017 are in `docs/api/error-codes.md` (new section "Audit report (AUD)") and in `problemWords.ts`. Every refusal on screen goes through the 0044 helpers. SDV-AUD-001 to -003 are marked as reserved for the audit list.
10. **Screens**: an **Audit report** tab, for Business admins under Business administration and for IT under IT. It holds:
    - the "New audit report" form, in the Reports exports' look;
    - the "Audit report register" table, newest first, with CSV and PDF per report;
    - "Verify an audit report": a CSV file, or a pasted fingerprint from the PDF.
    The Audit list's own sentences now include the three new actions.

## Decisions taken (the safer, smaller choice)

1. **The Audit report is its own tab, next to Audit**, rather than a button on the Audit page. IT has no Audit page, but the task gives IT the report. Under Business administration it sits beside Audit.
2. **Whole UTC days.** The stored end is the start of the day after the last day. The search ends 1 µs before it, so no event is counted twice across two reports with adjacent days.
3. **The CSV is stored in the register** (bytea), so a download is always the same bytes and its fingerprint never changes. Reports are capped at 10,000 events, so the row stays small.
4. **Verify takes the fingerprint, not the file.** The browser hashes the file, so no audit file is uploaded. A pasted fingerprint may use either case and may contain spaces or line breaks.
5. **Even the table owner can't change audit rows**: the trigger also refuses the owner. A schema change that needs to rewrite audit rows would have to drop the trigger in a reviewed changeset.
