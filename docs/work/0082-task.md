# 0082: Approvals from messages (integration I)

Drafted 2026-11-24 by task 0072; the design chat sets it `ready`. Branch `integration/i-approvals` from `release/vero-r7`. Starts after
0081 is merged; runs on Spring Boot 4.2 with `platform-core-v1.0.0`. Plan: `docs/work/0069-plan.md` (section 13 wins).

**Approved when set ready:** no new dependency; approval types for Vero's requests; a link key in the secret store (the path only in settings).

1. Types: print, download, lower a level, lower a record, redact on hold, release a hold, release an incident. Expiry per type is Vero's setting.
2. A link opens Vero's own approval page after sign-in and never decides by itself. The page shows what Approvals shows, no more.
3. Vero's `access_requests` is the one truth: the page decides through `AccessRequestService` (and the incident release service), with the same checks and audit: never one's own, never the placer of the hold, role held now. Then the link's request is closed; when that fails, Vero's decision stands and the link says "already decided". Decided in Vero first: the link says so.
4. Whole-record, held-redaction, hold-release and incident requests link to their review and are decided there, one at a time.
5. Refused links (expired, wrong person, role gone, changed) are audited through `ApprovalAudit` without the token. A link or token is in no log.
6. Nobody who may not decide gets a link: the requester and, for a hold release, who placed it.

Every rule of `CLAUDE.md` and the queue holds. Checks: full build; `npm test` and `npm run typecheck`; both schema checks;
`ui:capture` (on a scratch database when the local `sdv` isn't at this version); a run with the local mail sink. A test whose assertion must
change is listed in the report with the reason. Error codes, guides and runbook are updated in the same PR. Report
`docs/work/0082-report.md` with "No other product's name or behaviour in code" and "Decisions taken". Merge on green
`ci-passed`.
