# Task 0013: A separate schema step for customer installs

Written: 2026-11-18, by the design chat. Branch: `feature/install-1`, taken from `feature/admin-5`.

Background: report 0005 found that SDV changes the database every time it starts (Liquibase runs at startup). For on-premises installs the owner decided that the **customer's database team runs the schema step themselves**, the owner's team never sees the database owner's password, and **starting the app changes nothing**. Report 0005 also left one gap: no test starts the app against an empty database.

The owner approves the startup and build changes below by giving this task.

## Who sees this

| Part | Seen by |
|---|---|
| Schema step | The customer's database team (a command, not a screen) |
| "Database is older than this version" message | Installer and Platform operations (startup log and Health) |

## What to build

1. **Startup no longer migrates outside local mode.** Liquibase runs at startup only with the local profile (local mode stays exactly as today: migrations plus the local seed). Every other start skips it.
2. **Startup checks the schema instead.** If any changeset of this version has not been applied, the app does not start serving. It logs one plain line, and Health shows the same: "The database is older than this Vero version. Ask your database team to run the schema step (install guide, "Update the database")." If the database has changesets this version does not know, say that instead ("The database is newer than this Vero version").
3. **The schema step**, one command the database team runs with their own credentials (entered or from environment variables, never stored by Vero):
   - `status`: lists the changesets that would run;
   - `sql`: writes the SQL to a file, for teams that review and run SQL themselves;
   - `update`: applies them, including migration 018's concurrent indexes (`runInTransaction: false`).
   - It always uses the production context, so the local seed can never run through it.
   - Provide it as `Update-SDV-Schema.ps1` plus the same for Linux (`update-sdv-schema.sh`), running the bundled Liquibase from the application package. No new dependencies.
4. **Two database users.** Document that the schema step uses an owner user and the running app needs only read and write on the tables (no create or alter). Check that the app runs with such a user; if it can't (for example, something creates tables at runtime), stop and report.
5. **Install guide:** update `docs/operations/SDV_V1_GA_CLEAN_INSTALL_RUNBOOK.md` with a section "Update the database" (first install and upgrades: status, review, update, then start the app).

## Test against an empty database

Use a scratch database **inside** the existing `sdv-postgres` server, named `sdv_install_test`: create it for the test and drop it at the end. Never touch the `sdv` database. Do not create, remove or recreate any container.

1. Start the app (production context) against the empty scratch database: it refuses with the "older" message.
2. Run the schema step `status`, then `update`.
3. Start again: it starts, and the `tenants` table is empty (no seed data). (Creating the customer is the later shared setup command, not this task.)
4. Start again: nothing new is applied, and the startup is quick.
5. Script it as a repeatable check (`Test-SDV-CleanInstall.ps1`), and say in the report how long each step took.
