## Rule

A user can open a document only if their role allows its level: Standard for everyone with document access, Confidential needs VIEW_CONFIDENTIAL, Highly Confidential needs VIEW_HIGHLY_CONFIDENTIAL. The check is on the server, in the query or service, never only in the UI.

Put the list in the report. Every path in the list gets the check.

## 2. Records stay visible; restricted documents are locked (owner decision 2026-11-20)

The **document content** is what is restricted. The record's search fields stay visible and searchable for everyone with record access.

1. Search, quick search and record lists return records as today. Each record carries `restrictedLevel`: the highest level among its documents that **this user cannot open** (`CONFIDENTIAL` or `HIGHLY_CONFIDENTIAL`), or null. The UI shows it as a small lock icon next to the record identifier.
2. In the record's document list, a document the user can't open is returned **only** as: an opaque reference and its level. No file name, page count, received date, tags or comments.
3. Counts are unchanged (records are counted as today).
4. Opening, page images, thumbnails, print, download, redact, tag or comment on a document the user can't open: refused with a response that reveals nothing about it, plus an audit event (who, when, document ID, level).
5. Business metadata values are record-level and stay visible. If any metadata is stored per document rather than per record, list it in the report and treat it as document content (hidden).

6. Every check uses the **effective level** from task 0024 (the higher of document and record level), never the document's own level alone.

## 3. Print and download of Highly Confidential

Even a Restricted Steward is refused print and download of Highly Confidential documents in this task (the approval flow arrives in task 0028). Standard and Confidential print/download work as today for allowed roles, and Confidential ones are audited.

## Error codes (owner decision 2026-11-20, applies to every refusal in this task)

Every user-facing refusal or error returns a short, stable **code** plus a plain **message** in the error body, e.g. `{"code":"SDV-SEN-001","message":"This document is restricted."}`. Format: `SDV-<AREA>-<NNN>` (SDV = product; AREA = three letters such as SEN sensitivity, ROL roles, HLD legal hold, APR approvals, INT intake). Codes never change meaning once released. Each code is listed in `docs/api/error-codes.md` with: meaning, what the user should do, and what support should tell the customer. Other apps (for example the Platform Console runbook) read that list.
