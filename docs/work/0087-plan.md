# 0087: plan for remote testers through a tunnel

Date: 2026-11-24. Read from the code at `a958657` and from the providers' pages (section 8). Nothing was started, installed or changed.

## 1. Recommendation

**A named Cloudflare Tunnel with Cloudflare Access in front of Vero, and a second, tester-only Keycloak and database.**

```
Tester's browser --https--> Cloudflare --tunnel--> Caddy on the laptop, 127.0.0.1 only
  vero.<domain>   (Access: named emails)  -> screens (dist) and /api/ -> Vero, 127.0.0.1
  login.<domain>  (no Access, few paths)  -> tester Keycloak, 127.0.0.1
```

| | Cloudflare Tunnel + Access (**recommended**) | Tailscale Funnel | ngrok free |
|---|---|---|---|
| Cost | Free plan (a secondary source says up to 50 people; check at sign-up). Needs a domain on Cloudflare, usually a yearly fee | Free personal plan, non-commercial use only | Free: 1 GB out and 20,000 requests a month, probably too little for PDF pages |
| Testers install | Nothing | Nothing | Nothing (a warning page first) |
| HTTPS | Yes, own name | Yes, `ts.net` name, ports 443, 8443 and 10000 | Yes, one assigned name |
| Who can reach it | Only listed emails, with a one-time code, before anything reaches the laptop | Anyone with the address; no per-person limit found | Anyone with the address on the free plan, unless set up otherwise (not checked) |
| Switched off by | Stopping `cloudflared`, or removing the Access policy | `tailscale funnel off` | Stopping the agent |

Why: it is the only one of the three with a per-person gate found, and it has a fixed name of its own, which sign-in needs. A quick tunnel (`trycloudflare.com`) does not fit: for testing only, no uptime promise, and by its nature a changing name.

Alternative without a domain: Tailscale **Serve**. Each tester installs Tailscale and is let in by name. The free plan is for up to 6 users and non-commercial use.

Cloudflare ends the TLS connection, so it can see the traffic. Hence demo documents only, never real ones.

## 2. What must hold

1. **Never tunnel the local sign-in or the development server.** In local mode a request's headers say who you are. Its guard (loopback caller, `localhost` host) is no guard behind a local proxy: a tunnel also calls from loopback, and Vite's `/api` proxy may rewrite the host. Use the **release-type jar** (`target/sdv-web-…jar`; it has no local sign-in) with `SDV_AUTH_MODE=enterprise-jwt`, and the built `dist`.
2. **A development build is needed** (`Build-SDV-All.ps1` without `-Release`): only it trusts the demo licence, and no release licence keys exist. It warns at start. Fine for testers, never for a customer.
3. **Own database** (`sdv_testers`, in the existing server) and **own storage folder**, so testers can't reach or change the development data.
4. **Own Keycloak.** Changing the public address of the existing development one changes the issuer for everything else that uses it. Leave that container alone.
5. The laptop stays on, awake and online while testing. Expect it to be unavailable otherwise.

## 3. What Vero needs

| Matter | Setting |
|---|---|
| Vero's address | `SERVER_ADDRESS=127.0.0.1`. **Without it the release-type jar listens on every network card** (the local profile's setting doesn't apply). Own port, for example `SDV_SERVER_PORT=8292` |
| Sign-in | Issuer `https://login.<domain>/realms/vero-testers`, `SDV_AUTH_JWT_AUDIENCE` the API audience, provider ID as in the sign-in file. `SDV_AUTH_JWT_JWK_SET_URI` may be `http://127.0.0.1:<keycloak port>/realms/vero-testers/protocol/openid-connect/certs` (http is allowed on loopback). Vero reads the discovery document at the public issuer, so the laptop must reach `login.<domain>` |
| Sign-in file | A copy outside the repository: new `issuer`, `browserClientId`, `apiAudience`, own role mapping. Then setup `plan` and `apply` on `sdv_testers` |
| Redirect, origin | Client: public, code flow with PKCE S256, redirect and sign-out address `https://vero.<domain>/`, web origin `https://vero.<domain>`, RS256, audience mapper, groups claim, access token 15 minutes, no `nonce` in access tokens |
| Why no Access on `login.` | Vero fetches discovery, and the browser calls the token address from another origin. Access would answer both with its own login page |
| CORS at Vero | Nothing: screens and `/api/` share one origin, and Vero allows no other |
| Content-Security-Policy | The runbook's header with `connect-src 'self' https://login.<domain>`, sent by Caddy, with its other three headers. At Cloudflare switch **off** everything that adds scripts (Web Analytics, Rocket Loader, email obfuscation): the policy would block it |
| HSTS | `max-age=86400`, no `includeSubDomains`, no preload: a temporary name must not bind the rest of the domain |
| Cookies | Vero sets none; tokens are in memory. Keycloak's and Access's cookies are Secure over https. Access session 24 hours: when it ends, calls fail until the page is reloaded |
| Keycloak | Started in production mode with `hostname=https://login.<domain>`, `proxy-headers=xforwarded`, http on loopback only, own database, registration off, **brute-force detection on**, refresh token rotation on |
| Caller's address | `SDV_TRUSTED_PROXIES=127.0.0.1`, and Caddy must pass on the address `cloudflared` gives |
| Storage | `SDV_STORAGE_ALLOWED_ROOTS` only the tester folder, because an IT Admin tester can choose folders |
| Rate limits | Vero limits only intake (per sending system). **People's calls and sign-ins have no limit in Vero.** Use Keycloak's brute-force detection and a Cloudflare rate rule on `login.`; PDF work is limited (`SDV_PDF_MAX_CONCURRENT`, `SDV_PDF_MAX_PER_PERSON`) |

**Never reachable from outside.** Caddy answers 404 for everything not listed:

| Host | Allowed | Everything else, for example |
|---|---|---|
| `vero.` | `dist` files, `/api/` **except** `/api/v1/ingestion/` | `/actuator/**` (health and info are open in Vero), intake |
| `login.` | `/realms/vero-testers/`, `/resources/`, `/.well-known/` | `/admin/`, `/realms/master/`, `/metrics`, `/health`, port 9000 |
| no host | nothing | Postgres 5433, Vault 8200, Vero's own port, Vite 5183, the development Keycloak 8181 |

The tunnel lists only these two names and ends with a 404 rule. No router port is opened.

## 4. Tester accounts

| Person | Keycloak group | Vero role (`ENT-VERO-DEMO-0001`) |
|---|---|---|
| Reader | `BusinessUsers` | Business User |
| Steward | `DocumentStewards` | Document Steward |
| Business admin | `BusinessAdmins` | Business Admin (also in `…-0002`, for switching entities) |
| IT | `TenantITAdmins` | IT Admin |
| Restricted steward, if tested | `RestrictedStewards`, a new row in the testers' own role mapping | Restricted Steward; never together with an admin group (Vero gives neither) |

- One named account per person: own email, temporary password they must change, authenticator app required. No shared accounts: the audit names people. No Platform Operations Admin for testers.
- Group names must match the mapping exactly.
- **Data:** the demo seed only, with its own demo PDFs. Testers get a line that says "no real documents".
- **Permanent redaction can't be undone** by the seed's reset. Make a copy of `sdv_testers` after seeding, or drop and reseed that database.
- **Removing a tester:** (1) take the email out of the Access policy and revoke its Access session; (2) disable the Keycloak user and sign out its sessions. Vero keeps no session: a token already issued works until it ends (at most 15 minutes), but step 1 stops it from outside at once. Keep the account disabled rather than deleted, so audit entries stay readable.

## 5. Steps

**O** = owner only. **S** = a session can do it when told to, in a task of its own.

| # | Who | Step |
|---|---|---|
| 1 | O | Decide: Cloudflare with a domain (recommended), or Tailscale Serve. Get the domain and put it on Cloudflare |
| 2 | O | Create the Cloudflare account with two-step sign-in, and Zero Trust on the free plan |
| 3 | S | Write, as a task: `Caddyfile`, tester start and stop scripts (Vero on loopback, checks before start), Keycloak compose file and realm file (no secrets), tester setup files, a check script. **Adding Caddy, `cloudflared` and a Keycloak container needs the owner's yes** |
| 4 | O | Install `cloudflared` and Caddy. Create the Keycloak admin and database passwords and keep them under `C:\dev\sdv\secrets` or a password store |
| 5 | O | Allow and create the database `sdv_testers` and the Vault question in section 6. (The standing approval covers only `sdv`) |
| 6 | S | `Build-SDV-All.ps1`; schema step on `sdv_testers` (only with the owner's yes for that database) |
| 7 | S | Seed with the tunnel **off**: start the local jar on loopback on `sdv_testers`, run `Seed-SDV-Canvas-Demo.ps1 -Base … -Database sdv_testers` with the tester storage folders, stop it. The seed needs local mode, so this must be over before step 12 |
| 8 | O | Start the tester Keycloak, import the realm, create the admin, and the testers with their groups |
| 9 | O | `cloudflared tunnel login`, create the tunnel `vero-testers`, point `vero.` and `login.` to it. The credentials file is a secret: outside the repository |
| 10 | O | Access: an application for `vero.<domain>`, policy Allow with the testers' emails one by one, one-time PIN, session 24 hours. Rate rule on `login.` |
| 11 | S | Setup `plan` then `apply` on `sdv_testers` with the testers' sign-in file (`--replace-connection` if the seed left the demo connection). The database password stays in the environment |
| 12 | S | Start Vero (release-type jar, `enterprise-jwt`) and Caddy on loopback; run the local part of section 7 |
| 13 | O | Start the tunnel (`cloudflared tunnel run vero-testers`), from a phone on mobile data do the outside part of section 7 |
| 14 | O | Send each tester the address, their account and the "no real documents" line |
| 15 | O | **Off:** stop `cloudflared` first, then Vero, Caddy and the tester Keycloak. At the end: delete the Access application, the tunnel and the two DNS names; drop `sdv_testers` when the owner says so |

## 6. Open matters for the owner

1. The domain and provider (step 1).
2. Vault: the tester database uses the demo entities, so with the default prefix it uses the **same Transit keys** as development. Recommended for a short test with demo data: accept it. Separate keys need `SDV_VAULT_KEY_PREFIX` and a policy change in Vault, which is the owner's.
3. The live sign-in check with Keycloak (report 0065) has not been made. Make it first, locally: the same faults are harder to find through a tunnel.

## 7. Checks before testers get the address

Local: `netstat` shows Vero, Caddy and the tester Keycloak on 127.0.0.1 only; a request to Vero with local sign-in headers is refused (401); `/api/v1/session/sign-in` says `oidc` with the public addresses.

From outside:

| Request | Expected |
|---|---|
| `vero.` with no Access sign-in, or an email not listed | Access page; nothing reaches the laptop |
| `vero./actuator/health`, `/actuator/info`, `/api/v1/ingestion/…` (signed in to Access) | 404 |
| `login./admin/`, `/realms/master/`, `/metrics`, `/health` | 404 |
| `vero./api/v1/…` with local headers and no token | 401 |
| Sign in as each role, open a document, print, switch entity, sign out, reload | Works; no policy violation in the browser's console |
| Wrong password 10 times | Locked for a while |
| Disabled tester | Refused; in `vero.` at once |
