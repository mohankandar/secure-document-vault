# Task 0024: Sensitivity level on documents and on intake (S1 + S4)

Written: 2026-11-20, by the design chat. Branch: `feature/sensitivity-1`, taken from `release/vero-r7`.
Design: Lexavault project doc `SDV-Sensitivity-and-Quarantine.md` (sections 1, 6, 10) and `SDV-V1-Plan.md`.

**The owner approves the schema change below by giving this task.** No other schema change.

## Goal

Every document carries a sensitivity level, set by the source system when it is delivered. Nothing else changes for anyone yet: enforcement comes in task 0026.

## 1. Schema (through the separate schema step from task 0013)

1. `documents.sensitivity_level`: text, not null, default `STANDARD`, allowed values `STANDARD`, `CONFIDENTIAL`, `HIGHLY_CONFIDENTIAL` (check constraint).
2. Existing rows become `STANDARD` through the default. No other data change. The server still inserts nothing at start.
3. Index if the search queries will need it (say what you chose and why).
4. Update the reviewable SQL script and the schema version the server checks at start.

## 1a. Record (contract) level, added 2026-11-20 (owner decision; covered by the same schema approval)

The source may also set a level on the **record** (contract, patient file and so on), for example when migrating old contracts where every document is restricted.
1. Find where a record lives today (the business record behind search results; say which table) and add `sensitivity_level` there: same values, nullable, null = no record level.
2. **Effective level of a document = the higher of its own level and its record's level.** Put this in one place (domain), used by everything that checks levels. Documents that arrive later for that record get the record level automatically through this rule.

## 2. Domain and intake

1. A `SensitivityLevel` enum in the domain; `Document` carries it.
2. Every intake path (delivery API, any submission/ingestion path that creates documents) accepts an optional `sensitivityLevel`.
   - Missing: `STANDARD`.
   - Unknown or wrongly cased value: **refused with 400** and a clear message. Never guessed, never defaulted.
3. List every intake path you found and confirm each one handles the field.
4. Audit: the document-received audit event records the level.
4a. Every intake path also accepts an optional record-level `recordSensitivityLevel`, same rules: unknown refused with 400. If a record already has a level, a delivery may raise it but never lower it (a lower value is ignored and audited, not an error).
5. Update the API spec / API docs in `docs/api` with the field, its values and the 400 case.

## 3. Read side (no enforcement yet)

Return the level in the document detail the server already sends (field only). Do not filter anything yet.

## 4. Tests

- Missing level gives STANDARD; each valid value is stored; unknown and lower-case values are refused with 400.
- Upgrade: a database at the previous schema version moves to the new one with all existing documents STANDARD (use a scratch database such as `sdv_schema_test` in `sdv-postgres`, created and dropped by the test, like `Test-SDV-CleanInstall.ps1`).
- Clean install still passes.

- Record level: a document's effective level is the higher of the two; a later document on a restricted record is restricted; a delivery can't lower a record's level.
