# Task 0024: Sensitivity level on documents and on intake (S1 + S4)

Written: 2026-11-20, by the design chat. Branch: `feature/sensitivity-1`, taken from `release/vero-r7`.
Design: Lexavault project doc `SDV-Sensitivity-and-Quarantine.md` (sections 1, 6, 10) and `SDV-V1-Plan.md`.

**The owner approves the schema change below by giving this task.** No other schema change.

## Goal

Every document carries a sensitivity level, set by the source system when it is delivered. Nothing else changes for anyone yet: enforcement comes in task 0026.

## 1. Schema (through the separate schema step from task 0013)

1. `documents.sensitivity_level`: text, not null, default `STANDARD`, allowed values `STANDARD`, `CONFIDENTIAL`, `HIGHLY_CONFIDENTIAL` (check constraint).
2. Existing rows become `STANDARD` through the default. No other data change. The server still inserts nothing at start.
3. Index if the search queries will need it (say what you chose and why).
4. Update the reviewable SQL script and the schema version the server checks at start.

## 1a. Record (contract) level, added 2026-11-20 (owner decision; covered by the same schema approval)

The source may also set a level on the **record** (contract, patient file and so on), for example when migrating old contracts where every document is restricted.
1. Find where a record lives today (the business record behind search results; say which table) and add `sensitivity_level` there: same values, nullable, null = no record level.
2. **Effective level of a document = the higher of its own level and its record's level.** Put this in one place (domain), used by everything that checks levels. Documents that arrive later for that record get the record level automatically through this rule.

## 2. Domain and intake

1. A `SensitivityLevel` enum in the domain; `Document` carries it.
2. Every intake path (delivery API, any submission/ingestion path that creates documents) accepts an optional `sensitivityLevel`.
   - Missing: `STANDARD`.
   - Unknown or wrongly cased value: **refused with 400** and a clear message. Never guessed, never defaulted.
3. List every intake path you found and confirm each one handles the field.
4. Audit: the document-received audit event records the level.
4a. Every intake path also accepts an optional record-level `recordSensitivityLevel`, same rules: unknown refused with 400. If a record already has a level, a delivery may raise it but never lower it (a lower value is ignored and audited, not an error).
5. Update the API spec / API docs in `docs/api` with the field, its values and the 400 case.

## 3. Read side (no enforcement yet)

Return the level in the document detail the server already sends (field only). Do not filter anything yet.

## 4. Tests

- Missing level gives STANDARD; each valid value is stored; unknown and lower-case values are refused with 400.
- Upgrade: a database at the previous schema version moves to the new one with all existing documents STANDARD (use a scratch database such as `sdv_schema_test` in `sdv-postgres`, created and dropped by the test, like `Test-SDV-CleanInstall.ps1`).
- Clean install still passes.

- Record level: a document's effective level is the higher of the two; a later document on a restricted record is restricted; a delivery can't lower a record's level.

Follow `docs/work/README.md`. Include the list of intake paths and the schema version number.

## Part 2: record (contract) level — owner answers to report 0024, 2026-11-20

**The owner approves one more schema change for this part: the new table below.** Same branch, `feature/sensitivity-1`. Add a "Part 2" section to `0024-report.md` rather than a new report.

### Answers

1. **A new table** (your option b). 
2. **No submission-level default for documents.** Documents carry their own level on the upload; the record level covers "everything on this contract".
3. **Keep the 409** for a retry with a different level.

### 1. Schema (changeset 024, through the schema step)

`record_sensitivity_levels`: tenant, sending system (ingestion source), record key (the same normalized identifier values the record grouping uses in `findSubmissionIdsByRecordIdentity`, stored as one canonical text value), level (same three values, check constraint), reason, set by (`SOURCE` or the person), set at, updated at. Unique on tenant + sending system + record key. History goes to the audit trail.

### 2. Intake

1. The submission JSON accepts optional `recordSensitivityLevel` (remove it from `RecordSensitivityGuard`'s refusal). Exact names only; anything else 400. The upload header `X-SDV-Record-Sensitivity-Level` stays refused (one place to send it: the submission).
2. A delivery may **raise** a record's level, never lower it. A lower or equal value is ignored and audited ("record level kept at …"), not an error.
3. A submission without identifier values is a record on its own: its record level applies to that submission's documents only. Say how you handled it.
4. Update the OpenAPI file and `docs/api/README.md`.

### 3. Effective level

1. `SensitivityLevel.effective(document, record)` is now used wherever a document's level is read: record detail returns each document's own level **and** its effective level, and the record's level.
2. Documents that arrive later for a record with a level get it through this rule. Nothing is copied onto document rows.

### 4. Guard against losing a level

While any record level exists for a sending system, changing which fields are that system's record identifiers (or their normalization) is **refused** with a clear message giving the number of records with a level. Find every place identifier fields can change (admin screen API, setup command, schema scripts) and list them.

### 4a. Error codes (owner decision 2026-11-20, applies to every refusal in this task, including the ones Part 1 already added (unknown level, retry with a different level, record level on the upload))

Every user-facing refusal or error returns a short, stable **code** plus a plain **message** in the error body, e.g. `{"code":"SDV-SEN-001","message":"This document is restricted."}`. Format: `SDV-<AREA>-<NNN>` (SDV = product; AREA = three letters such as SEN sensitivity, ROL roles, HLD legal hold, APR approvals, INT intake). Codes never change meaning once released. Each code is listed in `docs/api/error-codes.md` with: meaning, what the user should do, and what support should tell the customer. Other apps (for example the Platform Console runbook) read that list.

### 5. Tests

Raise from a delivery; lower and equal ignored and audited; later document inherits the effective level; record without identifiers; unknown value 400; identifier change refused while levels exist and allowed when none; upgrade check from 023 to 024 like `Test-SDV-SchemaUpgrade.ps1`; clean install; full build. Then `npm run ui:capture` (the app is running and Vault is unsealed).
