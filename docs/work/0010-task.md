## Part A: Integrations (finding 14)

1. **List of sending systems**, each with a one-line status: "Working · last delivery 4 min ago", "Paused since 7 Oct", or "Waiting for the first delivery". Take it from the source summary endpoint.
2. **Detail:** "Sends documents to Vero through the API. 1,240 deliveries, 4,810 documents. Last problem: 15 Nov." Buttons **Edit** and **Pause receiving** / **Start receiving**.
   - Pause asks first: "While paused, Vero refuses deliveries from this system. It will need to send them again." The status change is audited as today.
3. **What it sends:** Field, Kind of value in words ("Text, digits only", "Text, capital letters", "Date"), Required, Used in search ("Yes · exact match"). Remove the "Not exposed by API" columns.
4. **Limits per delivery** in words: Largest PDF, Most pages in one PDF, Most documents, Wait for missing documents. Where the server reports no number for a platform default, show "Vero's standard limit" and say in the report which ones.
5. **How it proves who it is:** one sentence per type ("A client ID and secret kept in your sign-in system (Okta)"), plus "Vero stores only where the secret is kept, never the secret."
6. Source key, credential reference, field keys and versions, auth type code: under a folded **Technical details**.
7. Remove the Monitoring sub-tab; its numbers are in the status line and detail.

## Part A2: Add or edit a sending system (three steps)

1. **About it:** name, the source key (only when adding; it can't change later, say so).
2. **What it sends:** add, edit and remove fields with a kind of value and Required, in the same flow. "Changing a field later affects new deliveries only. Documents already stored keep the values they arrived with." If Tenant IT's API can mark which field identifies a record, add that column; if only the Business admin's API can, leave the column out and say so in the report (no permission change).
3. **How it signs in:** cards, one line each (client ID and secret in your sign-in system; signed token; certificate), then where the secret is kept (the credential reference), never the secret itself.
4. **Advanced (usually leave as is)**, folded: the limits.
5. Buttons: Back, Next, and on the last step **Save** and **Save as paused** (when adding). Vero can't test the connection itself (the other system calls Vero), so the new system shows "Waiting for the first delivery".

## Part B: Storage (finding 15)

1. Roles in words: "In use, new documents go here" and "Standby, used when <in-use volume> fills up", instead of ACTIVE/STANDBY and priority numbers. Keep priority in Technical details.
2. **How full**, with "Warns at 80% · stops at 95%". A banner when a volume passes its warning level: "primary-a is 82% full. At 95% it stops accepting documents and Vero switches to primary-b. Add space or a new volume before then." (If there is no standby, say "At 95% Vero stops accepting new documents.")
3. **Add a volume in three steps:** name and folder; **Vero checks it can write there** (show free space and the result); choose In use or Standby. "The folder cannot change later." Remove the "I have verified…" checkbox.
   - If the server has no way to check a folder before the volume exists, add `POST /api/v1/admin/storage-volumes/check` with the folder: same permission as creating a volume; uses the existing storage probe; writes and removes a small test file; returns writable and free space; audited as a check. Tests: refused without permission; unwritable folder reported plainly; nothing left behind.
4. Edit keeps the folder read-only.
