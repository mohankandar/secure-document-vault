# 0078: Records, values and search on case fields (integration E2)

Drafted 2026-11-24 by task 0072; the design chat sets it `ready`. Branch `integration/e2-values` from `release/vero-r7`. Starts after
0077 is merged; runs on Spring Boot 4.2 with `platform-core-v1.0.0`. Plan: `docs/work/0069-plan.md` (section 13 wins).

**Approved when set ready:** new table `records` and a record reference on submissions, access requests, record levels, quarantine filters; dropping the old value, definition, order and title tables at the end of the task; local and demo data re-seeded (nothing in production); the local schema step on the new local database.

1. A `records` row per entity, source and identity; `findByPrimary` at intake, then the claim; a race gives one record (tested with parallel deliveries). `RecordKey` ends as a key; existing references in URLs keep working or answer "not found" (no guessing).
2. Values through `FieldValues`, with Vero's legal holds given to it. Sensitive values: encrypted, exact search by fingerprint, read only for roles that open the document's level; never in a log, audit detail, CSV, report or admin page, except the record's identifier as today.
3. Search: free search and "contains"/"starts with" over fields that aren't sensitive; exact over sensitive ones; the screen says which. Without `pg_trgm` it says so (`PARTIAL_AS_PREFIX`).
4. Every admin read that joins the identifier (approvals, holds, reports, quarantine, restrictions, notices) uses the first primary in display order, through one class.
5. Level, quarantine and hold rules are unchanged: their tests run unchanged except for set-up.
6. Key-service calls: one for a record opened, two for a search on sensitive fields at most; a test counts them.
