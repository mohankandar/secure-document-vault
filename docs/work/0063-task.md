# 0063: Security fixes 2 (viewer exposure and resource limits, PDF intake)

Written: 2026-11-24 by the SDV design chat (LV-19). Branch `fix/security-2` from `release/vero-r7` after 0062. Vero-only.

The findings are in `C:\dev\sdv\queue\0061-security-findings.md` (local only, outside the repo). **The repository is public:** in commits, PR text and this report describe the fixes in plain terms, never how to use an unfixed weakness, and never copy the findings file into the repo.

**Approved:** code, config, test changes, a Liquibase changeset if needed, new codes. No new dependency.

1. **VSEC-3** exposure: pages, previews and text search require a valid viewing (opened first, same person, not expired); previews are audited once per viewing; the exposure and activity reports count page views and searches as exposure.
2. **VSEC-4** viewer limits: a global and a per-person limit on concurrent renders (over it: the busy answer, SDV-SYS-018 with `Retry-After`), a render time-out, **enforce `maxPagesPerPdf`** at intake and viewing, an image-size cap, PDFBox memory settings that spill to encrypted scratch, and catch out-of-memory per render so one file can't stop Vero. A load test in the report (parallel page requests on a large file: Vero stays up and answers busy).
3. **VSEC-20** PDF intake: refuse PDFs that can't be parsed, are encrypted, or carry active content (JavaScript, launch actions, embedded files), each with its own code, as a per-sending-system setting defaulting to refuse. A malware-scan hook waits for platform-core.
4. **VSEC-23** patterns: a length cap on every metadata value and a time limit on pattern checks.

Tests for each; full build, both schema checks, `npm test`, `ui:capture`. Report `docs/work/0063-report.md` with "No other product's name or behaviour in code". Merge on green `ci-passed`.
