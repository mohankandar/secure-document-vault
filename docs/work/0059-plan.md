# 0059 Part A: plan for Spring Boot 4.2

Date: 2026-11-23. Branch `plan/spring-boot-4`. No code changed.

**How it was made.** From Spring's own documents (cited as [n], list at the end) and a measurement: a copy of the
backend outside the repository was compiled and tested with `spring-boot.version` 4.2.0 and the 0058 override removed.
Items marked **measured** come from that run. The PostgreSQL-only tests, a real start of Vero, the schema step and the
UI were **not** run on 4.2.

## Summary

- Target: **Spring Boot 4.2.0** (on Maven Central since 2026-11-19; open-source support to 2027-12-31). Open-source
  support for 3.5 ended 2026-06-30. [1] Take the newest 4.2.x when Part B starts.
- It brings Spring Framework 7.1.0, **Spring Security 7.2.0**, Tomcat 11.0.27, Jackson 3.1.8, Liquibase 5.0.4,
  Flyway 12.11.0, HikariCP 7.1.0, JUnit 6.1.3. [2] Java 21 stays (4.2 needs 17 or later). [3]
- **Small:** imports. Measured: 5 main and 5 test files don't compile; all use Spring Boot classes that moved.
- **Large:** Jackson 3. Vero can compile and still be wrong. Measured: the published intake API answers **500 instead
  of its 400 or 409 codes** for a create-submission request with `metadata` or a level.
- **Blockers are all in platform-core** (section 2): the order of its identity auto-configuration, its Nimbus version,
  and the Spring versions it is built on.
- **One owner decision:** Liquibase 5 has a new licence (question 1).

**Measured result** (imports fixed, nothing else): 705 backend tests, 8 failures and 19 errors, all in `sdv-web`;
25 skipped as on 3.5. The other modules have no failure. The 27:

| Number | Cause |
|---|---|
| 15 errors | Jackson 2 mappers in tests no longer get date support (the jsr310 module has left the class path) |
| 8 failures | Intake API: Jackson 3 can't fill Jackson 2 `JsonNode` fields (contract test included) |
| 4 errors | `HealthGroupsTest` wiring |

### 1.3 Spring Security 7.2

`SecurityConfiguration` compiles unchanged, and `SignInChainTest`, `SignInKeysDownTest` and `SignInCodesTest` pass
(measured). Vero uses none of the removed parts: `and()`, `authorizeRequests`, `AntPathRequestMatcher`,
`MvcRequestMatcher`, `AccessDecisionManager`, login page. [8][9] To prove in Part B:

1. **Paths.** 7 matches with `PathPatternRequestMatcher` and wants absolute patterns (Vero's are). [9] Test each open
   path and its near misses (trailing slash, encoded, upper case): only the six open paths answer without sign-in.
2. **JWT `typ`.** 7 checks `typ` (JWT or absent) in `JwtTypeValidator`, part of the default validators, and no longer in Nimbus.
   [10] Vero sets its own validator list from `JwtValidators.createDefaultWithIssuer` (`OidcJwtConfiguration`).
   Test tokens with `typ` absent, `JWT`, `at+jwt` and nonsense, and compare with 3.5. **If the check falls out, add it explicitly.**
3. **`bearerFailures`** (sign-in hub away becomes 503 `SDV-AUT-004`): also prove on a live start.
   `SignInKeysAwareJwtDecoder` recognises `RestClientException`; check what 7.2's decoder throws when the hub is away.
4. **`.cors(withDefaults())`.** Framework 7.1 removed `HandlerMappingIntrospector`, which also served as a
   `CorsConfigurationSource`. [6] Vero defines no such bean. Check a live start and a cross-origin preflight; if either
   changes, set an explicit deny or remove the line.
5. **401 headers.** 7.1 adds a charset to `WWW-Authenticate`. [11] Compare with the published contract.

### 1.4 Jackson 3 (the main work)

Boot 4 uses Jackson 3 for HTTP; Jackson 2 can stay beside it. [4] Vero has 30 main and 32 test files on Jackson 2;
main code makes about 29 mappers by hand.

1. **The HTTP boundary must move in the same commit as Boot.** `SubmissionController` (`metadata`,
   `sensitivityLevel`, `recordSensitivityLevel`) and `FoundationAdminController` (`validationRules`, two places) take
   Jackson 2 `JsonNode`. Measured: 500 `SDV-SYS-013` in place of INT-008, INT-009, INT-010, SEN-002, SEN-004 and
   SEN-006. **Any Jackson 2 type in a request or response compiles and fails only at run time.** When the move is done a
   guard test must refuse `com.fasterxml.jackson.databind` and `.core` in Vero's code.
2. Rename packages; `JsonProcessingException` → `JacksonException`, which is **unchecked** (the compiler no longer points at missing
   `catch` blocks, so go through each one: those that fail closed must still catch); mappers through
   `JsonMapper.builder()` (immutable); renamed node methods. [5]
3. **Changed defaults.** [12] For each: decide and test.

| Default in Jackson 3 | For Vero |
|---|---|
| Properties sorted by name | Answers change order (harmless). **Stored, hashed or signed JSON must not change:** sealed audit details, `RecordKey`, `BusinessRecordRefCodec`, `RoleJson`, audit details: compare byte for byte |
| Dates as ISO text | Boot 3.5's HTTP mapper already does this; durations: compare |
| Unknown fields ignored | As Boot 3.5's HTTP mapper. A hand-made mapper that **relies on refusing** unknown fields must turn it on again |
| `null` for a primitive refused | Such a body becomes a 400: check against the contract |
| Text after the JSON refused | Stricter; keep |
| Depth limit 500 (was 1000) | Keep |
| Enums through `toString()` | Vero's main code overrides `toString()` in two places (`CallerAddress`, `SchemaVersion`); confirm neither reaches JSON |
| Parameter names detected | Check records and one-argument constructors |
| All modules on the class path register themselves [4] | Set `spring.jackson.find-and-add-modules=false` |

4. Tests: `MappingJackson2HttpMessageConverter` in 6 controller tests becomes the Jackson 3 converter;
   `findAndRegisterModules()` goes (dates are built in).
5. **Not recommended:** `spring-boot-jackson2` (deprecated stop-gap), or `spring.jackson.use-jackson2-defaults` for
   good. [4] The second may serve for one commit, to separate "renamed" from "changed".

### 1.6 Actuator, readiness and busy rules

- The property names Vero sets are unchanged; probes are now on by default. [4] Keep them written out.
- `HealthGroupsTest` proves the NOT_READY and BUSY rules. Measured: 4 of its 5 tests find no `HealthEndpoint` bean
  after the renames. The cause was not traced. **Until it passes with the same assertions, the readiness rules on 4.2
  are unproven.**
- Then live: no database at start, a full pool, hub away. Liveness stays UP; readiness is 503, and `SDV-SYS-018` with
  `Retry-After` when busy.
- HikariCP 6.3 → 7.1: the busy rule reads "`SQLTransientConnectionException` without a cause". Prove it on a real full
  pool.
- `/actuator/info` can show process details from 4.1, **including the working directory**. [14] Vero leaves `info` open
  **without sign-in**. Pin today's content with a test, and make sure the process part stays off.

### 1.7 Database

- No JPA or Hibernate ORM in Vero (Hibernate Validator goes 8.0 → 9.1).
- **Liquibase 4.31.1 → 5.0.4.** Compiles; `LiquibaseSeedContextTest` and `UsageReportingTest` pass (measured). To
  prove: **the checksums of all released changesets still match a database made by 4.31.1** (otherwise every customer's
  schema step stops); `status`, `sql`, `update`; the startup version check. Licence: question 1.
- **Flyway 11.7.2 → 12.11.0** (platform-core's runs): history tables made by 11 must be read by 12.
- The two schema checks use the jar under test throughout. **Missing:** a database made by the released 3.5 jar, then
  used by the 4.2 jar. Add it.

## 2. What blocks 4.2 today

| # | Blocker | Proposal |
|---|---|---|
| B1 | platform-core 0.6.1's `platform-identity-spring` names `org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration` (by its class-file strings, for ordering) and uses `@ConditionalOnBean`. Boot 4 moved its JDBC support into its own module with a new package. An order that names a missing class is ignored **without an error**, so identity beans may be missing at start. Read from the released jar, not run on 4.2 | platform-core's 4.2 release. Vero must not work around it |
| B2 | platform-core pins Nimbus **9.37.4** as a direct dependency; Security 7.2.0 is built on **10.9.1**, and Maven resolves 9.37.4. Vero's tests pass on that pair (measured), but token checking must not ship on it | platform-core drops or raises the pin. A pin in Vero only if that can't happen, with the owner's yes |
| B3 | platform-core 0.6.1 is built on Spring Boot 3.3.2 and Security 6.3.1; Boot strongly discourages one artifact for Boot 3 and Boot 4 [4] | Wait for the 4.2 release |

No third-party library was found without a version for 4.2.

## 3. Order of work, and how CI proves each step

CI keeps its jobs (backend with PostgreSQL, frontend, product-name guard, sender profile; `ci-passed`).

| Step | On | What | Proof |
|---|---|---|---|
| 0 | 3.5 | Tests that record today's behaviour **before anything moves**: published answers, stored JSON byte for byte, `typ` cases, open paths and near misses, 401 headers, `info` content, `null` and trailing text in bodies | `ci-passed`; own PR, merged |
| 1 | 3.5 | Guard test: Jackson types in requests and responses, with today's places as the only exceptions | `ci-passed`; own PR, merged |
| 2 | 4.2 branch | platform-core's 4.2 release, Boot 4.2.x, moved imports, override removed, Jackson 3 at the HTTP boundary (inseparable, 1.4) | Backend job green; contract tests unchanged |
| 3 | same | The rest of Jackson 2, guard list emptied, starters renamed | Step 0's tests unchanged |
| 4 | same | Health test wiring; readiness, busy and hub-away live | `HealthGroupsTest`, same assertions; live run in the report |
| 5 | same | PostgreSQL-only tests, both schema checks, and "made by the 3.5 jar, used by the 4.2 jar" | Backend job; scripts |
| 6 | same | `Build-SDV-All.ps1`, `npm test`, full `ui:capture`, live Keycloak delivery as in 0041 | Report |
| 7 | | One PR, merged on green. Steps 2 to 6 are not merged one by one: a half-moved Vero is not a release | `ci-passed` |

**Rule from step 2 on:** a test may change its imports and set-up. An assertion that must change is listed in the report with the
reason.

**Going back.** The task has no schema change, so the 3.5 jar must still start on a database the 4.2 jar's schema step
has touched. Prove it in step 5.

## 4. What Vero expects from platform-core's 4.2 release

1. Every module built and tested on Spring Boot 4.2.x, Framework 7.1, Security 7.2 and Java 21, in one BOM version.
2. `platform-identity-spring` and `platform-outbound-spring`: ordering by the new class names, with a test that their
   beans appear in a Boot 4.2 application (B1).
3. Nimbus as Security 7.2 declares it, or no pin (B2).
4. The names Vero uses kept, or listed in the release notes: `IssuerFetch`, `OidcTestSignIn`, `DevelopmentLicence`,
   `LicenceSigningKey`, `PlatformGroupAuthorization`, `EntityMembershipResolver`, the JDBC stores, `IdentitySchema`,
   `LicensingSchema`, `SetupCommand`, `MockIssuer`, `ProfileValidator`, `ProfileContract`, `platform.outbound.*`.
5. Migration SQL unchanged byte for byte (identity V4, licensing V1), tested with Flyway 12.
6. No Jackson 2 in public types (none was found in the modules looked at in 0.6.1).
7. The setup jar runs on 4.2's library versions; the failure analyzers are still registered.
8. Release notes naming the Spring versions and every changed default.
9. Whether 0.6.x keeps getting security fixes for Vero releases still on 3.5, and until when.

## Questions for the owner

1. **Liquibase 5 licence.** 4.2 brings Liquibase 5.0.4 under the Functional Source License (FSL-1.1-ALv2), which is not
   an open-source licence; each version becomes Apache 2.0 after two years. Liquibase says production use stays free
   and the limit is on competing offers. [15] Vero ships it inside its jar. Recommended: take 5.0.4 once your legal
   reader has agreed; otherwise pin 4.33.0 (Apache 2.0; Vero doesn't use Boot's Liquibase start-up code) and prove it.
   This is not a legal opinion.
2. **Steps 0 and 1 can be done now, on 3.5**, without platform-core. Approve them as their own task? (Recommended.)
3. Is a date known for platform-core's 4.2 release? Until then Vero stays on 3.5, past its open-source support.
