# Task 0005: Home screen, and date indexes for search

Written: 2026-11-17, by the design chat, after report 0004 (approved). Branch: `feature/ui-home`, taken from `feature/ui-search-2`.

The owner approves the two small backend changes in Part B and the migration in Part C by giving this task.

## Who sees this

| Part | Seen by |
|---|---|
| Home tab and page | Business user, Document steward (`SEARCH_RECORDS`) |
| Recently viewed | Each person sees only the records they opened themselves |
| Needs attention | Business user, Document steward: only records their search may return |
| "Open documents" from Home | Business user, Document steward (`VIEW_PDF`) |

Business admin, Tenant IT and Platform operations have no Home tab; they land on their own area as today.

## Part A: the Home page (design screen 1, `docs/design/vero-ui-after.html`)

1. A **Home** area tab before **Records**, and the page people with `SEARCH_RECORDS` land on after signing in.
2. Greeting with the person's first name ("Good morning, Maya") from the session's `displayName`; no greeting name if there is none.
3. The same search bar as Records (task 0003 and 0004 behaviour). Searching from Home moves to Records with the results.
4. **Recently viewed** (Part B): up to 8 records, each with identifier, the first preview fields and when the person last opened it ("12 minutes ago"). Clicking one opens it in Records with its record panel. Empty state: "Records you open will show here."
5. **Needs attention**: up to 5 records with missing documents from the last 30 days, each as "300000000090 · name · 1 of 2 documents received". A "Show all" link opens Records filtered the same way. Empty state: "Nothing needs attention."
6. The "Ask Vero" card on the design is a marker for a later release: **do not show it in the product build.** Keep the space so it can be added later without moving the layout.
7. Phones: the cards stack.

## Part B: two small backend additions

1. **Recently viewed:** `GET /api/v1/business/me/recent-records?limit=8`.
   - Built from the person's own `DOCUMENT_VIEW_OPENED` audit events in their tenant: newest first, one entry per record.
   - Return only records the person may still see now (same checks as search and record detail; nothing past retention or deleted).
   - Requires `SEARCH_RECORDS`. Never returns another person's activity.
   - Check that reading it stays fast for a busy user; if it needs an index, it goes into Part C.
2. **Needs attention:** an optional `incompleteOnly` flag on the existing search request. With it, only records with an incomplete submission are returned. It counts as a criterion, like a date range, so it can be used alone. Same authorization and paging as search.
3. Backend tests for both: own activity only, nothing beyond retention, the flag alone and with a date range.

## Part C: date indexes (decision 1 from report 0004)

1. A migration adding indexes so date-only searches do not read every submission for a source: tenant + source + received date, and tenant + source + last-updated date (and whatever Part B needs).
2. It must run through the normal schema step, the one customers run themselves before starting the app (startup inserts or changes nothing). Note in the report how it behaves on a large existing table; if it would lock the table for long, say how to run it without that.
3. Check the query plans before and after and put the result in the report.
