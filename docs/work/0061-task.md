# 0061: Independent security review of Vero (findings only)

Written: 2026-11-24 by the SDV design chat (LV-19: decided as recommended). Same shape as platform-core's step 3 (P042). Branch `review/security` from `release/vero-r7`. **Read only: change no product code.**

Review Vero as an attacker and as a bank's security reviewer would, **as if you didn't build it** (don't rely on earlier reports' claims; check the code):
- sign-in and machine tokens (client-ID binding, claims, `typ`, audiences, a person's token used as a machine caller), sessions, CSRF, CORS;
- authorisation on every endpoint: roles, levels, quarantine, legal hold, separation rules, entity isolation (one entity can never see another's data), admin views never showing content;
- intake: file size and type checks, PDF parsing risks, idempotency, unidentified attempts, trusted proxies, busy answers;
- storage and encryption: keys, envelope encryption, fingerprints, temporary files, what is logged;
- the one-time grant, print and download paths, exports and their fingerprints, the sealed audit report and append-only trail;
- the frontend: XSS, what is kept in browser storage, error text;
- dependencies (Maven and npm) against known advisories; CI and workflow permissions; scripts that handle secrets.

Write `docs/work/security-findings.md`: each finding with an ID (`VSEC-n`), severity (Critical, High, Medium, Low, Info), where (file and line), how it could be used, and the fix you'd propose. Commit it on the branch, push, open a PR, merge when `ci-passed` is green (docs only). Report `docs/work/0061-report.md` with the counts by severity. Every Critical, High and Medium finding becomes a fix task (the design chat writes them).
