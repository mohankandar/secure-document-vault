# 0065: Real sign-in in the browser (production)

Written: 2026-11-24 by the SDV design chat (LV-19). From security finding VSEC-29 (Info, but a blocker for any customer): Vero's screens never start a real sign-in; only the local test sign-in works. **No customer can use Vero without this.** Branch `feature/browser-sign-in` from `release/vero-r7` after 0064.

Rules already decided: sign-in is set by the installer through setup (one login connection per customer and product, platform-core identity); the person signs in with the customer's own login system (for example Okta), lands on their last entity, and switches entities in the header. No sign-in settings in Vero's screens.

## Part A: plan (read only, then continue with Part B unless something needs the owner)
`docs/work/0065-plan.md`: authorization code flow with PKCE against the active login connection (discovery from the connection's issuer); where the code exchange happens (browser public client, or Vero's backend as a confidential client: recommend one with reasons); token storage (memory only, VSEC-22); refresh and sign-out (no `id_token_hint` in a logout address); `nonce` check or no ID token use; the error screens with codes; what the install runbook asks the customer's IT to set up in their login system. If a choice needs the owner, list it and stop.

## Part B: build
As planned: the flow, the callback, session expiry, sign-out, entity landing; **VSEC-11** (require `exp` and `iat`, a default maximum token lifetime, refuse an audience equal to the browser client ID and tokens carrying `nonce`/`at_hash` at the API); **VSEC-22** (tokens in memory only; a Content-Security-Policy for the app, documented for the serving proxy). Live check with the local Keycloak: a person signs in through the browser, lands on an entity, opens a document, signs out. Tests; full build; both schema checks; `npm test`; `ui:capture` with a sign-in step. Report `docs/work/0065-report.md` with "No other product's name or behaviour in code". Merge on green `ci-passed`.
