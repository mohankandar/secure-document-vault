# 0069: plan for Vero on platform-core 1.0 (draft)

Date: 2026-11-24. **A draft.** platform-core 1.0.0 isn't released: this is written against the documents at tag
`platform-core-v1.0.0-rc.2` (read through GitHub) and Vero at `5eff6ae`. Points marked **[recheck]** must be looked at
again against 1.0.0. The design chat's project documents (switch-over guide items, Vero's retention design) were not in
this session; where they matter the plan says **[design chat]**.

## 0. Before any of it

| | State | Needed |
|---|---|---|
| 0067 | platform-core 0.7.0 on a branch, identity tables to version 5 | Owner's schema step, then merge |
| 0070 | Spring Boot 4.2 | Everything below needs it (1.0 requires Boot 4.2) |
| 0065 Part B | Browser sign-in | Not needed by the modules, but their screens need real sign-in to be shown to a customer |

Nothing is in production, so **no customer data is migrated**. Local and demo data is dropped or re-seeded where a table
goes away; each section says which. The sealed audit and `audit_events` are append-only and stay.

## 1. Order and sizes

platform-core's own order (switch-over guide section 3) with Vero's dependencies:

| # | Task | Depends on | Size |
|---|---|---|---|
| A | BOM 1.0.0, public-API check, error codes and reference form | 0070 | S |
| B | Monitoring | A | M |
| C | Licensing on: state shown, intake stopped after grace, usage recorded | A | L |
| D | Customer keys and `platform-crypto` (drop `sdv-crypto`) | A | L |
| E | Case fields | D | XL (3 tasks: definitions; values and search; screens and intake) |
| F | Erase log and retention through it | D, E | L |
| G | Outbound for everything, integrations | A | S now |
| H | Notifications | C, A | L |
| I | Approvals through notifications | H | M |

B, C and D can run one after another in any order. E is the risk; F must follow E because the record's fields are erased
through the log only.

## 2. BOM, codes, references (A)

- **Changes:** `platform.core.version` 1.0.0; Vero's schema step runs identity 5 and licensing 2 (both exist) and adds each
  new module's run with its own history table (`SchemaStep`, `DatabaseSchemaCheck`, both checks' expectations). New tables
  for the app user are covered by the default privileges, but three grants are narrower than that (licensing
  `lic_last_seen`, `lic_clock_reset`; erase log `erl_position`): the schema step takes rights back, as it does for the audit.
- **Config that stops the start:** `platform.licensing.trusted-keys*` must go; the licence keys are in Vero's build
  (`META-INF/platform/licence-keys.json`, `licence-build.properties`). `SDV_TRUSTED_KEYS_FILE` is Vero's own and goes away
  with them: activation then uses the build's keys. The demo seed's development licence needs a development build.
- **References:** platform-core's are `R-…`; Vero's are UUIDs (0062). Keep Vero's until monitoring (B), then use one form.
- **Risk:** the public API is frozen from 1.0.0 only: **[recheck]** names used by `PlatformIdentityReads`, `IssuerFetch`,
  `OidcTestSignIn`.

## 3. Monitoring (B)

- **Changes:** Vero's checks (schema, database, sign-in keys, storage folders, intake attempts) become app checks; database,
  key service, login system, licence come from the module. The Health and Problems pages read the check list. A diagnostic
  bundle for support (no secrets, no content) on Platform operations › Health.
- **Goes away:** `SignInKeysHealthIndicator`'s own polling, parts of `Operations` health code.
- **Keep:** readiness semantics documented in the runbook (NOT_READY, BUSY, 503 with `Retry-After`): the module's readiness
  must not turn Vero away because a side system is down. Wire its checks into `/actuator/health/dependencies` only.
- **Decision proposed:** a down login system stays a readiness matter (as today); mail, integrations and folders never.
- **Data:** none. **Risk:** start-up refusal: the module refuses when a required dependency is down, Vero starts and keeps
  trying when the database is away. Recommendation: `startup-checks=false` for the database until the runbook changes.

## 4. Licensing (C)

Today the licence is stored and read when a slot is activated; nothing checks the allowance.

- **State:** `LicenceService` state on Business administration and IT › About; the app starts in every state except
  missing/forged/wrong customer (that is the module's rule). **After grace, intake stops**: `SubmissionController` create,
  document upload and finalization refuse with a new code and 503, no `Retry-After` **[recheck the code and status with the
  ingestion contract: a new minor version]**. Viewing, download, print, export, redaction, holds, approvals go on.
- **Usage:** recorded, never enforced: stored bytes and documents per entity; **concurrent agents** (people active in the
  last 15 minutes, daily peak) and **named stewards/admins** (people whose sign-in gave those roles in the month)
  **[design chat: the exact seat rules]**. Meter points: `ActiveTenantFilter` (a signed-in request), a daily job, the
  storage report's counts. No names leave: the ledger holds numbers.
- **Tables:** `lic_` only. Vero keeps the export anchor of the last usage file (one new small table).
- **Screens:** Licence page for Business Admin (state, slots, usage against allowance), export for IT. Never a price.
- **Goes away:** `SDV_TRUSTED_KEYS_FILE`, the development-key special case.
- **Data:** demo licence re-issued by the seed. **Risk:** a wrong clock at a customer stops intake after a false expiry:
  the module warns first; the runbook gets its clock-reset section.

## 5. Crypto (D)

Vero's `sdv-crypto` (574 lines): AES-256-GCM in chunks, key per document from Vault Transit, one Transit key per entity.
`StreamCipher` is the same framing with another magic and associated data.

- **Changes:** one `StreamingCryptoPort` over `StreamCipher`; `EnvelopeInfo` fills the existing columns of
  `document_crypto_metadata` and `sealed_originals` (profile `platform-stream`). Associated data gets the document's ID as
  context, which closes VSEC-13 (ciphertext not bound to its document): check that `StreamCipher` takes a context per stream
  **[recheck]**.
- **Keys:** **per customer, not per entity.** Today each entity has its own Transit key (`sdv-tenant-<id>`). Moving to
  customer keys is the platform's model; isolation between a customer's entities is then by associated data and access, not
  by key. **Question 1.**
- **Vault:** policies `platform-crypto-app` and `-setup`, created by the customer's IT; Vero's running token loses key
  creation (closes VSEC-34). `customerKeys` in `product-roles.json` from `optional` to `required` (setup then makes them).
- **Goes away:** module `sdv-crypto`, `SDV_VAULT_*` in favour of `platform.crypto.vault.*` (AppRole or token file),
  `VaultTransitKeyProtectionProvider`, `KEY-…` codes replaced by `CRYPTO_…` ones in the screens' words.
- **Data:** local and demo documents can't be read with the new format. Recommendation: **no reader for the old one**: the
  seed re-delivers; other local documents are dropped by a new database. **Question 2** (the owner's local data).
- **Order inside:** replace, run the clean-install check with a scratch Vault mount, then remove. **Risk:** the local
  persistent Vault must get a mount and policies: an owner step, never done by a session.

## 6. Case fields (E)

Vero has its own model: `metadata_field_definitions` (per sending system, versioned rows), `business_metadata_values`
(readable), display order, record titles, and the first-field rule of 0056.

- **Definitions:** `platform-fields` per entity and product. "Which fields a source sends", record titles and search
  visibility are Vero settings by key (`putExtension`). The design's table maps each type and rule; `BOOLEAN` becomes a
  dropdown, `DATETIME` gets its offset.
- **Primary:** the `primary` flag replaces `PrimaryIdentifierRule` / `PrimaryIdentifierSql` (the code's comments foresee it).
  Several primaries are allowed by the model: Vero needs one for admin pages: first primary in display order, as its own rule.
- **Values:** `FieldValues` per record. **Vero's record is a group of submissions under one key** (`RecordKey` from
  identifier values), platform-fields' is a record ID. Proposal: a real `records` table (entity, source, record ID), each
  submission pointing to it; `findByPrimary` finds it at intake. This replaces `RecordKey` in `record_sensitivity_levels`,
  `access_requests`, quarantine filters and references. It is the largest change in the plan.
- **Sensitive fields:** stored encrypted, found by exact match only, shown to roles that may see them. Consequences: free
  search across fields (0022), "starts with" and "contains" skip them; results, CSVs and reports show them only to document
  roles; quarantine filters match by fingerprint; names and addresses are sensitive by default, so **searching people by a
  part of their name ends by default**. **Question 3.**
- **Import of a field list:** Business administration › Search fields: choose the file, see the report (conflicts by key),
  confirm. Export too.
- **Contract:** the ingestion contract stays (fields by key); validation answers map to Vero's codes; a delivery's values are
  checked by platform-fields' rules (its own limits: 512 characters against Vero's 4,000 since 0063): a contract change.
- **Tables gone:** `metadata_field_definitions`, `metadata_field_display_order`, `business_metadata_values`, title tables.
- **Data:** dropped and re-seeded; `pg_trgm` is asked of the customer's DBA (optional).
- **Size:** three tasks, about a third of the whole plan. **Risk:** search speed at scale (0052/0055 numbers must be measured
  again with encrypted values), and the 1:1 move of every admin read that uses the primary join.

## 7. Erase log and retention (F)

Today: retention claims a due document, deletes the file, then keeps the row as `EXPIRED_DELETED`; sealed originals (0066)
are destroyed after the hold; redaction deletes the old file.

- **Kinds and handlers:** `document` (file, storage reference, data key), `sealed-original`, `replaced-version` (redaction),
  `case-fields` (built in, when the last document of a record goes). Each handler: check (legal hold, quarantine), erase,
  verify. Erase only through `Eraser`.
- **Work guard:** `EraseGuard.mayTakeWork()` in a filter beside the schema gate: intake, viewing, everything but health.
  Scheduled jobs check it too. New coded answer, readiness 503.
- **Order matters:** one failing entry stops later erasures. The Health page shows the pending entry (IDs and code only).
- **Replay:** `--erase-replay` for the Vero jar; runbook section; the recovery manifest tools learn it.
- **Log location:** outside the database's storage, shared by all instances: a new install requirement, and a storage
  folder that must not be one of the document volumes.
- **Retention design:** "erase handlers per kind, replay before work" **[design chat]**: whether a record's search fields go
  with its last document, and what the audit keeps.
- **Tables:** `erl_position`. **Data:** none; a local log starts empty for a new database. **Risk:** a database belongs to
  one log for good: the scratch databases of the checks need their own location each.
- **0066:** "erase-log hook" for sealed originals is this task's handler.

## 8. Outbound and integrations (G)

Vero calls nobody except Vault and the login system. `platform-outbound` is in for the test sign-in. Integrations (sending
out, watched folders) are not planned; the sender profile (0041) stays as the published way in. **Nothing to do** until a
customer needs an outbound integration. **[recheck]** that Vault calls may keep their own client.

## 9. Notifications (H)

- **Events** (Vero's `EventCatalogue`): technical (T, IT Admin): intake refused or incomplete deliveries, storage near full
  or full, unidentified attempts, key service down. Business (B, per entity): approval waiting, request decided (to the
  requester), quarantine incident opened or released, legal hold placed or released, role conflict, retention run with
  failures; licensing events from C.
- **Text:** event, entity, counts, times, a link. **Never a record number?** The module allows one. Recommendation: none for
  Highly Confidential, none in Teams or Slack. **Question 4.**
- **Recipients:** people of a role in an entity: Vero doesn't store people. Needs addresses: from sign-ins seen (e-mail claim)
  or fixed lists by the admins. Recommendation: lists first. **Question 5.**
- **Screens:** IT › Notifications (connect mail, Teams, Slack by secret path; health), Business administration ›
  Notifications (which events, where, how often).
- **Secrets:** a `SecretResolver` over Vault KV (`secret/data/platform/*`, read). **Tables:** `notif_` (8).
- **Goes away:** nothing; `steward_notices` and in-app requester notices stay.
- **Zones:** identity is the one source (`idn_customer.time_zone`, `idn_entity.time_zone`): `tenants.time_zone` goes away.
- **Risk:** a message must never say that a Highly Confidential document exists to someone who may not know.

## 10. Approvals from notifications (I)

- Links in mail open Vero's own approval page after sign-in; opening never decides. Types: print, download, lower a level,
  lower a record, redact on hold, release an incident.
- **Vero's `access_requests` stays the source**: `notif_approval_request` holds the link's request, and deciding goes
  through `AccessRequestService.decide` (same checks, same audit, never one's own). `ApprovalAudit` writes link refusals.
- Records and redactions on hold: link to the review, decided on the page one at a time. Same expiry as Vero's setting.
- **Risk:** two stores of one truth: the link's state follows Vero's, never the other way round.

## 11. What goes away, in one list

`sdv-crypto`; `metadata_field_definitions` and its value, order and title tables; `PrimaryIdentifierRule` and `…Sql`;
`RecordKey` as a key; `tenants.time_zone`; `SDV_VAULT_*`, `SDV_TRUSTED_KEYS_FILE`, `SDV_DEFAULT_TIME_ZONE`; parts of the
health code.

## 12. Questions for the owner, each with a recommendation

1. **Keys per customer instead of per entity?** Recommended: yes (the platform's model; destroying one customer's keys is
   then one step). A customer that wants keys per entity would be a platform-core change.
2. **Local documents unreadable after D:** may they be dropped and re-seeded? Recommended: yes, with a new local database
   made beside the old one, which is kept until the owner deletes it.
3. **Names and addresses sensitive by default, so no partial search on them?** Recommended: keep the platform's default; a
   Business Admin can switch it off per field before data arrives.
4. **Record numbers in messages?** Recommended: only in e-mail, never for Highly Confidential, never in Teams or Slack.
5. **Where do recipients' addresses come from?** Recommended: lists kept by the admins first; sign-in addresses later.
6. **Vero refuses intake after grace:** 503 with its own code, so senders keep and retry? Recommended: yes, with a
   contract version, because a 4xx would make some senders give up.
