## Goal

A Business Admin can put a document on legal hold so automatic retention deletion can never remove it, and release the hold later. The Business Admin never opens the document to do this.

## 1. Schema

Legal hold storage: document ID, tenant, reason (required, 3–500 characters), placed by, placed at, released by, released at. One active hold per document; history kept.

## 2. Server

1. Place and release a hold, capability MANAGE_LEGAL_HOLD (Business Admin). The Business Admin finds documents by the record's **primary identifier** (contract number, patient number: whatever the tenant's identifier field is), and sees only that identifier, level, received date and page count, never title, file name or content. The internal document ID is never shown on admin screens (keep it in the API response for support only).
2. `RetentionDeletionService` skips any document with an active hold, and says so in its run summary (count only).
3. Corrective redaction is still allowed on a held document (it replaces the file; it does not delete the record).
4. Every place and release is audited.

## Error codes (owner decision 2026-11-20, applies to every refusal in this task)

Every user-facing refusal or error returns a short, stable **code** plus a plain **message** in the error body, e.g. `{"code":"SDV-SEN-001","message":"This document is restricted."}`. Format: `SDV-<AREA>-<NNN>` (SDV = product; AREA = three letters such as SEN sensitivity, ROL roles, HLD legal hold, APR approvals, INT intake). Codes never change meaning once released. Each code is listed in `docs/api/error-codes.md` with: meaning, what the user should do, and what support should tell the customer. Other apps (for example the Platform Console runbook) read that list.

## Tests

A held document past its retention date is not deleted; after release it is deleted on the next run; non-admins refused; tenant isolation; audit events written.
