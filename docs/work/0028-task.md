## 1. Schema

Access requests: ID, tenant, document ID, kind (`PRINT`, `DOWNLOAD`, `LOWER_LEVEL`), requested level (for LOWER_LEVEL), reason, requester, requested at, status (`PENDING`, `APPROVED`, `DECLINED`, `USED`, `EXPIRED`), decided by, decided at, expires at, used at.

## 2. Raise and lower the level

1. Raise (CHANGE_SENSITIVITY_LEVEL, with reason): applies at once. Only to a level higher than now. A Steward may raise to Highly Confidential and then can no longer open the document.
2. Request lower (CHANGE_SENSITIVITY_LEVEL, with reason): creates a LOWER_LEVEL request. A Steward can only request lowering from Confidential. Applies only when approved.
3. Audit: who, when, from, to, reason.

4. The same raise / request-lower rules apply to the **record level** (task 0024): raising applies at once; lowering needs a Business Admin approval (request kind `LOWER_RECORD_LEVEL`, with the record identifier instead of a document ID on the approvals list).

## 3. Highly Confidential print and download

1. A Restricted Steward requests PRINT or DOWNLOAD for one document, with a reason.
2. A Business Admin (APPROVE_SENSITIVE_ACCESS) approves or declines.
3. An approval is a grant for **one document, one use**, expiring 24 hours after approval (configurable per tenant). `ControlledDownloadService` and the print path accept a Highly Confidential document only with a valid, unused, unexpired grant for that user and that kind, and mark it USED.
4. **Nobody approves their own request.**

## 4. Approvals list for the Business Admin

Server endpoint listing pending requests with **only**: request ID, kind, the record's **primary identifier** (contract number, patient number: the tenant's identifier field), the document's received date and page count (or the record's document count for a whole-record request), a **scope** (`DOCUMENT` or `RECORD`, shown as "One document" / "Whole contract"), the document's position on the record ("document 2 of 6") when two documents on it share the same received date and page count, level, requested level, requester, reason, requested at. No title, file name, other case fields or content. The internal document ID is not shown on the screen (it may stay in the API response for support).

## 5. Working through many requests (owner approved the compact Approvals design, 2026-11-20)

1. The pending list supports filters by kind and by requester, sorts oldest first, and returns records grouped by primary identifier (or gives what the UI needs to group).
2. **Bulk decision:** approve or decline a list of request IDs in one call; each is checked and audited on its own, and the response says which succeeded. Requests with scope `RECORD` (whole contract) are **refused in bulk**: they are decided one at a time.
3. **Expiry of pending requests:** a pending request nobody decides becomes `EXPIRED` after 7 days (configurable per tenant); the requester sees it as expired. Separate from the 24-hour use window of an approved grant.

## Error codes (owner decision 2026-11-20, applies to every refusal in this task)

Every user-facing refusal or error returns a short, stable **code** plus a plain **message** in the error body, e.g. `{"code":"SDV-SEN-001","message":"This document is restricted."}`. Format: `SDV-<AREA>-<NNN>` (SDV = product; AREA = three letters such as SEN sensitivity, ROL roles, HLD legal hold, APR approvals, INT intake). Codes never change meaning once released. Each code is listed in `docs/api/error-codes.md` with: meaning, what the user should do, and what support should tell the customer. Other apps (for example the Platform Console runbook) read that list.
