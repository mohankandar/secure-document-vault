# 0065 Part A: plan for sign-in in the browser

Date: 2026-11-24. Read from the code at `aa95dd5`; nothing was changed or run. **No choice needs the owner** (section 11).

## 1. Today

- `src/auth.ts` has an authorization-code flow with PKCE (S256) and state, but no screen starts it (`beginOidcLogin`,
  `handleOidcCallback` have no caller), so a production build can't sign anyone in.
- It takes issuer, client ID and redirect address from build-time `VITE_OIDC_*` settings; keeps the access and ID tokens
  in `sessionStorage`; puts `id_token_hint` in the sign-out address; has no refresh.
- The server side works: bearer tokens, platform-core's `idn_` tables, entity choice (`X-SDV-Entity-Id`,
  `EntityChoice.tsx`, last entity kept in the browser, switches audited). `idn_login_connection` already has
  `issuer_uri`, `browser_client_id` and `api_audience`, filled by setup.
- `switchEntity` reloads the page. With tokens in memory only, that would sign the person out.
- Nothing documents how the built screens (`dist`) are served in production.

## 2. Where the code is exchanged: in the browser (public client)

| | Browser public client with PKCE (**recommended**) | Backend as a confidential client |
|---|---|---|
| Secret | None to keep | A client secret per customer, stored and rotated |
| Server | Stays stateless, no cookies, so no CSRF surface | Server sessions, cookies, CSRF protection, sign-out on every node |
| Schema, dependencies | None | A session table, probably a new dependency |
| If a script gets into the page | It can read the token in memory while the page is open | It can't read the token, but can call the API through the session all the same |
| Customer's IT | Must allow the web origin for the token address (CORS) | Must hand over a secret |

The difference that matters (reading the token) is reduced by memory only, short lifetimes, refresh rotation and a
Content-Security-Policy (section 8). A backend client stays possible later without changing the API, which takes bearer
tokens either way.

## 3. Settings come from the server, not the build

New open endpoint `GET /api/v1/session/sign-in` (`no-store`), answering only:

```
{ "mode": "oidc", "authorizationEndpoint", "tokenEndpoint", "endSessionEndpoint" | null, "clientId", "scope", "provider" }
```

- From the ACTIVE connection with Vero's configured provider ID, issuer and audience. None: `503` and no endpoints.
  Local sign-in: `{ "mode": "local" }`.
- The server fetches the discovery document with platform-core's `IssuerFetch` (https, no redirects, the customer's proxy
  and CA), checks that its `issuer` is the connection's and that the addresses are https (http only for loopback); cached
  5 minutes, the last good copy kept 1 hour.
- Scope: `SDV_AUTH_BROWSER_SCOPE`, default `openid profile email`.
- `VITE_OIDC_*` goes away, so one build serves every customer. `VITE_SECURITY_MODE=LOCAL` stays for development builds.

## 4. The flow

1. Start without a token: ask the endpoint. On a normal start, go to the login system at once; after a sign-out or an
   error, show "Sign in to Vero" with one button instead, so nobody is caught in a loop.
2. Make `state` (32 random bytes) and the PKCE verifier (64). Both, and the route to come back to, are in
   `sessionStorage` for the round trip only (they are not tokens; single use, refused after 10 minutes).
3. Login system, then `<origin>/` with `code` and `state`. Clean the address bar, check state (and `iss` when the answer
   has one), exchange once (the single-flight guard exists).
4. Keep the access token, its end and the refresh token **in memory only**. An ID token is thrown away unread.
5. Load the session and entities and land on the last entity (as now); the chooser when there is none.

**No `nonce`, no ID token use.** The task allows either. Vero needs no ID token: the API reads the person from the access
token, and PKCE plus state bind the answer to this browser. It also lets the API refuse any token with a `nonce`.

## 5. Expiry, refresh, reload, several tabs

- Refresh at 80% of the lifetime and after a wake-up, when there is a refresh token (single flight; the new one replaces
  the old). A failed refresh keeps the token until it ends.
- Ended or refused (401): keep the screen and show "Your sign-in has ended" over it with "Sign in again", so nothing typed
  disappears unread. After signing in, back to the same route and entity.
- **Reload or a new tab:** no token, so the flow starts by itself; with the login system's own session it returns without
  a question. This follows from "memory only"; the IT guide says so.
- `switchEntity` no longer reloads: it remounts the app with a new key. A test must show that nothing of the old entity
  stays on screen or in the stores.
- Idle sign-out stays the login system's matter (its session and token lifetimes).

## 6. Sign-out

Forget the tokens, then go to `endSessionEndpoint` with `client_id` and `post_logout_redirect_uri` (**never**
`id_token_hint`). Without one: "You are signed out of Vero. Your company sign-in may still be open." A revocation address,
when offered, is called first for the refresh token (at most 2 seconds). Other tabs are told by a `BroadcastChannel`
message without a token.

## 7. The API's token checks (VSEC-11)

In `OidcJwtConfiguration`, for people and sending systems:
- `exp` and `iat` required; `iat` not in the future (60 s allowed).
- Longest lifetime: `SDV_AUTH_JWT_MAX_TOKEN_LIFETIME_SECONDS`, default **7200** instead of 0 (off), because some login
  systems give about 90 minutes by default. 0 is refused from then on: an upgrade note.
- `nonce` or `at_hash`: refused. `typ`: `JWT` and `at+jwt` accepted (the library refuses the second today), others refused.
- The API audience equal to the connection's `browser_client_id`: Vero refuses to start (`SDV-SYS-005`), and the check
  runs again when the connection is read.

All answer 401 with a sign-in code; the log names the check, never the token.

## 8. Content-Security-Policy (VSEC-22)

Sent by the serving proxy (documented), and a `<meta>` tag in `index.html` as a floor (it can't carry `frame-ancestors`):

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' blob: data:; font-src 'self';
connect-src 'self' <login system origin>; frame-src 'self' blob:; object-src 'none'; base-uri 'none';
form-action 'self'; frame-ancestors 'none'
```

- `connect-src` needs the login system's origin for the token call; the proxy knows it. The meta tag, being in the build,
  says `connect-src 'self' https:`.
- To check in Part B: the print frame uses `document.write` with blob pictures and an inline style. The tour must run
  under this policy with no violation.
- Also `X-Content-Type-Options`, `Permissions-Policy` and `Referrer-Policy: no-referrer` (a code never leaves in a Referer).

## 9. Error screens and codes

New codes (next free ones, from `SDV-AUT-014`), each in `error-codes.md` and the screens' words. The login system's own
text is never shown.

| Code | When |
|---|---|
| AUT-014 | Sign-in is not set up, or no connection is in use |
| AUT-015 | The login system can't be reached (discovery or token address) |
| AUT-016 | The answer doesn't belong to this browser's sign-in (state, age, `iss`): "Start again" |
| AUT-017 | The login system refused, for example access denied |
| AUT-018 | Signed in, but the API's checks (section 7) refuse the token; the log says which |

Codes for no role, no entity and an inactive customer exist and keep their screens.

## 10. What the customer's IT sets up (install runbook)

1. A **public** single-page client: authorization code with PKCE (S256), no implicit flow, no secret.
2. Redirect and sign-out address `https://<vero>/`, exact; web origin `https://<vero>`.
3. An access token for Vero's API audience, signed RS256, with the groups and name claims, life at most 2 hours (15 to 60
   minutes advised). The API audience must not be the client ID.
4. Refresh tokens with rotation (optional).
5. The sign-in file: `issuer`, `providerId`, `browserClientId`, `apiAudience` (all there already), then `setup apply`.
6. The proxy: serves `dist`, sends `/api` to Vero, sends the headers of section 8, TLS only.

With notes for Okta (Trusted Origin with CORS, a custom authorization server), Entra (single-page platform redirect, the
API's scope) and Keycloak (Web origins, audience mapper).

## 11. Choices made, and why none needs the owner

Public client, memory only (the task), settings from the server, no nonce, two hours, no idle timer. All can be changed
later without touching stored data, and none needs a password, a purchase, or a GitHub or machine setting. One thing may
become an owner step in the live check: if the local development login server's client `sdv-web` does not list
`http://localhost:5183` as a web origin, changing that is the owner's.
