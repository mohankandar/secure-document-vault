## What to build

1. **CI on every push and pull request** to `release/vero-r7` (and `main` later):
   - backend: full build and all tests, PostgreSQL 16 on a service container, so the PostgreSQL-only tests run too (they are skipped locally);
   - frontend: `npm ci`, typecheck, build;
   - the product-name guard (below);
   - the sender-profile contract tests, once 0041 adds them (leave a clearly named job that 0041 fills, or add it in 0041).
2. **No platform-core yet in this task.** CI builds Vero as it is today, **except** the old Enterprise Identity 0.2.0 can't be fetched by a runner. So this task also makes the identity dependency point at **platform-core's released `platform-identity-*` modules from `platform-core-v0.1.0`** (coordinates `com.documentplatform.platform`, via `platform-bom`), with **no code change beyond imports and coordinates**: the Java packages are unchanged (`Setup-Design.md`, interface check). If anything else breaks, stop and report; the full identity move is task 0041.
   - Locally the same build must work: document the one-time `settings.xml` entry (a personal token with `read:packages`, kept outside every repo) in `docs/install/` and the README.
3. **Product-name guard:** a test in Vero's build that refuses other products' names (LexaVault, platform-core is allowed as a library name) in code, SQL, JSON, YAML, scripts and install guides, any case, whole word. Test and demo data included. Exceptions only in a listed file with a reason; today's known uses are fixed in 0041, so until then the guard lists them as exceptions with "fixed in 0041".
4. **Report the owner's GitHub settings exactly:** branch protection for `release/vero-r7` (required check name, PRs required, no direct pushes), and the package access for this repo in platform-core's package settings.
5. Merge through a PR; it must be green before merging. If `gh` can't merge, stop with the PR open.

Tests: CI green on the PR. Locally: full build, `.\Seed-SDV-Canvas-Demo.ps1 -Reset` (owner runs it if the session's permission check refuses), `ui:capture`. Report `docs/work/0042-report.md`, with "No other product's name or behaviour in code" (or the listed exceptions).

## Update from the board (SH-12, SH-13, 2026-11-22): platform-core is released

- **Use `platform-core-v0.2.0`** (the newest release; BOM `com.documentplatform.platform:platform-bom:0.2.0`), not v0.1.0. Read its release notes (`docs/releases/platform-core-v0.2.0.md` in platform-core, read only).
- Registry `https://maven.pkg.github.com/mohankandar/platform-core`, **server id `github-platform-core`**.
- **Locally:** `~/.m2/settings.xml` has a server `github-platform-core` that reads the token from the environment variable **`GITHUB_PACKAGES_TOKEN`** (a classic personal token with `read:packages` only, set up by the owner). If it isn't set up, stop and report.
- **In CI:** the job uses its own `GITHUB_TOKEN` (the owner gives the Vero repo Read access in platform-core's package settings); `.github/maven-settings.xml` reads it from the environment. No token in any file.
- The identity schema needs **V3** before running on 0.2.0. In this task only the coordinates move; if the build or tests need the platform schema run, stop and report (that is 0041's work).
- **Change (owner, 2026-11-22):** CI reads the packages with the repository secret **`PLATFORM_PACKAGES_TOKEN`** (GitHub refuses secret names starting with `GITHUB_`) (the owner's read-only token, set with `gh secret set`), not with the job's own `GITHUB_TOKEN`, because platform-core publishes one package per module and granting Actions access to each one by hand is error-prone. `.github/maven-settings.xml` reads `${env.GITHUB_PACKAGES_TOKEN}`; the workflow passes the secret `PLATFORM_PACKAGES_TOKEN` into the environment variable `GITHUB_PACKAGES_TOKEN`, so the same settings file works locally and in CI. The report says the token expires and must be renewed in both places (laptop variable and repo secret).
