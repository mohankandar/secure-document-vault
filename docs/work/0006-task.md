## Part B: page previews (backend)

Today every page image is a full render (`DocumentViewerService.renderPage`): scale 0.5–2.5, the whole document decrypted per request, and a `DOCUMENT_PAGE_VIEWED` audit event per page. Using it for previews would write a "page viewed" event for every page of a document the moment it opens, and decrypt it once per preview.

1. Add `GET /api/v1/business/documents/{documentId}/viewer/previews?first=1&count=12` (follow the existing viewer path):
   - same checks as the viewer: `VIEW_PDF`, tenant, document `AVAILABLE`, same verified plaintext;
   - decrypts the document **once** per request and returns small previews (fixed width about 120 px, PNG) for pages `first` to `first+count-1`; `count` at most 24;
   - built from the **current** PDF, so redacted areas are black in previews too;
   - same no-store headers as page images;
   - **no audit event per preview.** Opening the viewer already writes `DOCUMENT_VIEW_OPENED`; previews are part of that. Pick a simple response shape (for example JSON with a data URL per page) and say which in the report.
2. Tests: role without `VIEW_PDF` refused; other tenant's document refused; non-`AVAILABLE` document refused; `count` above 24 refused; no audit event written; previews of a redacted document come from the redacted PDF.
3. Measure in the report: time for 12 previews of the largest demo document, and memory use if it is noticeably higher than one page render.
