# Task 0011: Problems and Audit in plain words

Written: 2026-11-18, by the design chat. Branch: `feature/admin-4`, taken from `feature/admin-3`.

Design: boards "Platform operations · Problems" and "Platform operations · Audit" in `docs/design/vero-admin-after.html` (approved). Findings 12, 17 and 18.

The owner approves the backend additions in Part C (including migration 020) by giving this task.

## Who sees this

| Part | Seen by |
|---|---|
| Problems tab | Platform operations; Tenant IT read-only (`VIEW_TECHNICAL_FAILURES`, finding 12) |
| Audit tab | Platform operations |

Nobody can fix a problem from this screen today: recovery happens by the sending system sending again (retry is in the sending system's API). So the tab is read-only for both roles and says who to ask.

## Part A: Problems (findings 12 and 18)

1. Platform operations tabs become: Overview, Problems, Storage, Health, Audit, About. "Intake" and "Incidents" merge into **Problems**; old addresses open Problems. Tenant IT gets a **Problems** tab (between Integrations and About) showing the same list.
2. Filters as chips with counts: All, Could not store, Stuck, Missing documents.
3. Rows: Record (number and record title, from Part C), What happened as a sentence ("The PDF is password-protected", "Still being stored after 2 days", "2 of 4 received"), From (sending system name), Since ("2 days ago").
4. **Detail panel**, three blocks:
   - **What happened:** "Vero received appraisal.pdf from the Loan Origination System on 15 Nov and tried 3 times. The file is locked with a password, so Vero cannot read or protect it."
   - **What it means:** "The record shows 2 of its documents. This one is not stored and nobody can open it in Vero."
   - **What you can do:** "Ask the loan team to send an unlocked copy. It arrives as a new delivery; nothing to retry here."
   - **Copy a note for the loan team:** plain text with record number, file name, what happened and what to send. No document content, no personal data beyond the record number and file name.
   - Error code, document, submission and source IDs, attempts: under folded **Technical details**.
5. Write the sentences for every processing error code the server can produce (list them from the code), plus a general fallback ("Vero couldn't store this file (code X)."). Put the code-to-sentence table in one file and list it in the report.
6. Remove the text about producer APIs and "retry finalization" from the screen.

## Part B: Audit (finding 17)

1. Each row reads as a sentence: "Maya Okafor opened loan-agreement.pdf", "Daniel Reyes tried to download title-deed.pdf without permission", "Priya Natarajan changed how long to keep new documents to 7 years", "Loan Origination System delivered 3 documents". Columns: When, What happened, Record, Result (Done / Refused / Failed).
2. One sentence pattern per action code, in one file; a fallback for unknown codes ("<person> · <humanized code>"). List the table in the report.
3. **Everyday filters:** activity (grouped: Opening and reading, Downloads and prints, Changes to documents, Settings changes, Deliveries, Refused), person, period (Today, Last 7 days, Last 30 days, custom dates without time boxes), record number. Action code, actor type, actor ID, target and correlation ID under **More filters**.
4. Routine events stay hidden by default as today ("Include view events"), and document opens stay visible (decision in report 0005).
5. Detail panel: the sentence, when, result, then folded **Technical details** with codes, IDs and the safe details.
6. **Export:** CSV of the filtered list (sentence, time, person, record, result, action code). Exporting is itself audited.

## Part C: backend additions

1. **Problems carry the record:** each problem in the operations summary includes the record's identifier, record title (task 0009), file name and sending system name. Tests: tenant isolation; a problem whose record can't be resolved still appears, without a title.
2. **Names in the audit, going forward:** migration 020 adds the actor's display name to new audit events, taken from the signed-in session (the same name shown in the account menu); sending systems use their display name. Older events have none: show the subject ID for them. Never backfill or change existing audit rows. Tests: new events carry the name; events without one still list.
3. **Audit list carries the record:** for document events, the audit list returns the record identifier and file name (looked up at read time). Same permission as today.
4. Record-number filter on the audit list.

## Rules
